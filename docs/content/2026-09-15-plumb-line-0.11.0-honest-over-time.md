# plumb-line 0.11.0 — honest over time

plumb-line 0.11.0 is out on npm, PyPI, and the Claude Code marketplace. The
milestone was called "Honest over time", and the three things it ships are
all about what happens to a value after the moment it was checked.

The first is a golden baseline. A derived value can now be pinned together
with its whole provenance envelope, and a later run that produces a different
value gets a finding that names which input moved: a lineage step whose
source went from `real` to `fallback`, a confidence score that vanished, a
transform label that changed. Accepting a new state requires a written
reason. A snapshot test tells you the number changed; this tells you why.
Principle 9 had been labelled `not-implemented` on the roadmap since July,
and it is now `current` in both languages, held to parity by a shared
case table.

The second is a GitHub Action. It reads one manifest, runs whatever
enforcement the repository actually carries, and writes a single SARIF log.
It ships no default checks and no default globs; a capability the manifest
omits is never counted as a pass, and a tool the runner lacks is a finding
rather than a clean check. Upload to code scanning is wired, and this repo's
own CI uploads nothing, so ingestion stays unobserved until an adopter
reports it.

The third is the ratchet, the one that makes adoption possible without
demanding zero.
Turning the output-tagging lint on in a 300k-line repository fails everywhere
at once, so nobody turns it on. The ratchet pins today's untagged output
sites, by file and function name, in a committed file. From then on a pinned
site is reported as a note and only a new site fails the build. Shrinking the
set is silent; growing it needs a reason, recorded in the file's history. The
Action runs the check and never writes the file; the only two commands that
write it are `update` and `prune`. A count could not have enforced this,
because a change that fixes one site and adds another leaves the count
unchanged. It is proven end to end in Python; the JavaScript site marker is
unit-proven at the rule and the assembler.

One detail from the release process is worth recording. The pre-tag harness
dispatched its six blind auditors by invoking the audit skill through the
installed plugin, and the installed plugin was 0.9.0, one release behind. All six
found every planted violation. All six failed the report-format checker,
because they had been running a skill from before the format rules were
tightened. The checker caught it before anything was scored. The run was
discarded, the auditors were re-dispatched against the checkout's own skill
file, and the failure turned out to point at three rules the current skill
implied without stating. Those are stated now, the runbook says which file an
auditor reads, and the re-run passed 6/6 on findings and 6/6 on format. The
harness caught a fault in how the harness was being run, which is the
behavior it exists to have.

Also in this release: the remediate skill was re-validated under
deadline and gate pressure, and both runs refused to relabel a mock so a
release gate would pass; import-linter's install hints are pinned to the
version its text parser was tested against, with the machine-readable output
that would retire the parser requested upstream; and a step-summary counter
that could only ever read zero is gone.

Before the tag: 6/6 blind auditors PASS, 2/2 remediators PASS, recorded in
[validation-results.md](../validation-results.md). The self-audit of the
release diff found nine findings, seven violations and two needs-review,
every one a place where the project's own docs promised more than its
tooling enforced; six fixed before the tag, three
deferred as tracked issues, one pre-existing spec note filed.
