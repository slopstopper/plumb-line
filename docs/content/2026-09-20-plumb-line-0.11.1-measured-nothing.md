# plumb-line 0.11.1 — a green job that measured nothing

plumb-line 0.11.1 is out on npm, PyPI, and the Claude Code marketplace. It
is a patch: seven fixes to the ratchet and the GitHub Action that shipped in
0.11.0, every one of them filed as an `audit-deferral` issue while that
release was being built and reviewed. Two of the seven change what the
Action refuses.

The ratchet pins a repository's untagged output sites in a committed file
and fails the build when a new site appears, or when the file itself is
missing or invalid. The first of those rests on the surface having been
measured. In 0.11.0 it was possible for the surface to go unmeasured and the
job to stay green: a typo in `outputGlobs`, or a glob that stopped matching
after a directory moved, left the capability with nothing to lint, a count
of unmeasured surfaces in the head line, and an exit code of zero. A ratchet
over a surface nothing ran on is a standing claim with no evidence under it,
so 0.11.1 treats it the way a missing tool was already treated: when the
manifest names a ratchet and any output capability went unmeasured, the job
fails regardless of `fail-on`, with one line per capability naming it, why,
and the globs that were supposed to find it. Jobs without a ratchet are
unchanged. The fixture assertion in this repository's own CI now checks the
unmeasured list is empty, so a fixture whose globs drift is caught at the
pull request.

The second change closes the same gap one file at a time. A file inside the
output surface that ESLint could not parse, or a Python file with a syntax
error, used to leave the capability marked as run, so `update` could pin a
set computed as though that file had no sites. The capability now carries
`unparsed surface file: <path>`, `apply` neither splits nor prunes it,
`update` and `prune` refuse, and under the first change the job fails. There
is no override flag; the fix is to make the file parse. Pinned sites in that
capability report at error level until it does, which surfaces as new code-
scanning alerts rather than as notes.

The rest is smaller. The report-format checker read an inline principle name
hard-wrapped across two lines as the wrong name, which is how one of the two
0.11.0 remediation records failed it (#397); it now joins soft-wrapped prose
before matching, and tables, fences and key lines are never joined. A failed
ratchet write no longer leaves a temp file inside `.plumb-line/`, and a
failing cleanup cannot hide the original error. The ESLint rule's site
naming goes through one helper, and a destructured export gets a stable
derived name instead of colliding with an anonymous default export. The
runner and the ratchet module now reach each other only through public
names, with a test that scans both sources for private reaches in either
direction.

The JavaScript half of the ratchet was unit-proven in 0.11.0 over recorded
ESLint output and is now proven through the Action itself: a new fixture
carries a two-site output surface and a ratchet, the clean tree pinning both
sites and the broken tree pinning one so the second reads as new, and CI
runs both trees. ACTION.md's maturity note states what that run proves and
what it does not: `js.provenance` runs and parses there and detects nothing,
since the fixture enables only the output rule.

Before the tag, the harness ran because the diff touched the adapters, even
though the audit skill itself did not change. Six blind auditors found every
planted violation and confirmed both clean fixtures clean. Four of the six
reports passed the format checker. All six had been told to read nothing in
the checkout beyond the skill and the principles; four ran the checker on
their own output anyway, one from a copy outside the checkout, and the two
that took the instruction literally are the two that failed. The record
files the restriction as a rig defect first, before the scores, and still
counts one of the failures, a glossary rendered inside a code fence, as a
real wobble in the skill's output. One false positive is recorded too: an
auditor read the boundary config's `target` and `from` keys reversed and
reported a working guard as inverted.

The self-audit of the release diff found six findings, three violations and
three needs-review, all in the ratchet and report-format machinery that the
two behaviour changes made load-bearing. One of the needs-review items is
fixed in the release: the audit report the README links as its example
carried "format-validation: clean" from a checker that this same patch
changed, and nothing re-ran the checker over committed reports; the test
suite now does. Two were already tracked. Three are deferred as tracked
issues in the next patch, including the observation that a destructured
site's derived name still changes if the pattern is reformatted.
